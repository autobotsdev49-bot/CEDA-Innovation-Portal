# Engineering Choices

Use this guide before adding a dependency or engineering pattern. **In use** means the root code implements it today. **Planned** means the team has selected it for the stated feature. **Deferred** means revisit it only when the listed need arises. Locations under `src` refer to the project root.

| Area | What to use and why | Where and status |
| --- | --- | --- |
| Rendering | **SSG (Static Site Generation)** builds shared public HTML ahead of requests. Use it for informational pages that rarely change. **SSR (Server Side Rendering)** builds a response on the server using the current request. Use it for signed-in pages with fresh protected state. **RSC (React Server Components)** let pages read server data without shipping that code to the browser. Use client components for forms, dialogs and Optimus Prime chat. | Planned in `src/app` public and protected route groups. In a pull request, name the route and justify the rendering strategy. |
| Rendering behavior | **CSR (Client Side Rendering)** lets browser code update interactive parts of the screen. **Hydration** makes server-rendered interactive elements respond to input. React's **reconciliation** compares the previous and new UI descriptions and updates the **DOM (Document Object Model)**. Use predictable markup and keep the first screen small. Review layout changes and avoid repeatedly measuring and changing layout in the same loop. | Planned in route and shared UI components. Use a loading boundary with React Suspense only where content waits independently and the fallback is accessible. |
| Performance | **LCP (Largest Contentful Paint)** measures when the main visible content appears. **INP (Interaction to Next Paint)** measures responsiveness. **CLS (Cumulative Layout Shift)** measures unexpected movement. **TTFB (Time to First Byte)** measures how quickly the response starts. Reserve media dimensions, use optimized images and fonts, defer nonessential assets, and use framework code splitting and tree shaking to limit downloaded JavaScript. | Planned in the public routes, shared components and browser checks. Record a mobile Lighthouse baseline and investigate slow cases with real interaction tests. Use performance budgets after measuring typical pages. |
| State | **Local state** keeps input and dialog behavior close to the component. **Server state** keeps durable applications, permissions and decisions in the database. **Derived state** is calculated from data already available. **URL (Uniform Resource Locator) state** supports shareable filters without exposing sensitive values. Use explicit workflow transitions and revision checks for autosave. | In use as immutable assessment inputs and computed recommendations in `src/features/assessment/round.ts`. Forms, database persistence, route filters and revision-controlled autosave are planned. |
| Networking | **REST (Representational State Transfer)** gives the portal predictable resource URLs and HTTP responses. **BFF (Backend for Frontend)** places the portal's request validation and orchestration behind a same-origin server boundary. Use bounded cursor pagination, cancellation for obsolete searches, sensible timeouts and safe retry with backoff. An **idempotency key** lets a repeated write return the same result when safe. Use bounded polling first for chat, then scoped live updates if needed. | Planned in `src/app/api/v1` and server feature adapters. Record request contracts, permissions and concurrency behavior in [API Contracts](<API Contracts.md>). |
| Caching | **CDN (Content Delivery Network)** and browser caching can reuse public assets. Version asset names or URLs when their content changes. Set sensitive HTML, session responses and downloads to private and no-store. Keep drafts, credentials and support transcripts out of persistent browser storage. | Planned in public routes, protected route handlers and download adapters. Test cache behavior with distinct user accounts. |
| Architecture | **Separation of concerns** gives each place one job. Pages display flows, server handlers validate and authorize, feature modules express business rules, and the database enforces durable and concurrent invariants. Use shared UI components and design tokens for consistent labels, spacing and focus. | In use in `src/features`, `scripts` and `tests`. Planned in `src/app`, `src/components`, `src/lib/server` and `supabase/migrations`. Keep one web application and use flags only for reversible rollout choices. |
| Security | **XSS (Cross-Site Scripting)** is unwanted script execution. Keep user text escaped and avoid raw HTML. **CSRF (Cross-Site Request Forgery)** is an unwanted authenticated action triggered by another site. Check write origins and apply framework-appropriate protections. **CSP (Content Security Policy)** restricts what browsers may load and which sites may frame the portal. **CORS (Cross-Origin Resource Sharing)** controls which external origins browsers permit to read cross-origin responses. Keep portal requests same-origin by default. | Planned in HTTP headers, input schemas, rendering, server routes and review tests. See [Security Accessibility and Operations](<Security Accessibility and Operations.md>). |
| Identity and access | **HTTPS (Hypertext Transfer Protocol Secure)** encrypts traffic. **MFA (Multi-Factor Authentication)** adds a staff identity check. **RLS (Row Level Security)** restricts database access row by row. **JWT (JSON Web Token)** carries signed claims and needs verification. Recheck live role, scope and session state for sensitive operations. **PKCE (Proof Key for Code Exchange)** protects authorization-code exchanges when the chosen flow uses it. Keep secrets on the server, use appropriately scoped cookies, time out stale sessions and review dependencies. | Domain release checks are in use in `src/features/assessment/round.ts`. Actual Supabase authentication, grant lookup, session checks and RLS are planned in server adapters and migrations. |
| Accessibility | **WCAG (Web Content Accessibility Guidelines)** 2.2 AA is the target. Prefer semantic HTML, labels, alt text, keyboard navigation, visible focus and reduced-motion support. **ARIA (Accessible Rich Internet Applications)** adds semantics when native controls are insufficient. Provide announcements for changing state, accessible dialogs, zoom and reflow checks, and captions or transcripts for publishing media. | Planned across public, applicant and staff routes. Test automated violations with axe and manually check a keyboard, screen reader and high zoom. Prepare reusable date, number and language formatting. |
| Observability and tests | **Unit tests** check one rule or small group of rules. **E2E (End to End) tests** verify whole browser journeys. **CI (Continuous Integration)** runs checks when changes are proposed. **A/B testing** compares controlled variations. Use redacted logs, request correlation, browser journeys with Playwright, error tracking and a rollback procedure when deployment exists. | Unit tests and synthetic A/B checks are in use in `tests/autobotsDev.test.ts`. Browser, database, contract and CI checks are planned. No real A/B participant results exist. |

## Abbreviations in the code and reviews

**API (Application Programming Interface)** is the contract a caller uses to request data or actions. **HTTP (Hypertext Transfer Protocol)** defines how browser requests and responses are sent. **HTML (HyperText Markup Language)** gives pages their structure and accessibility landmarks. **SEO (Search Engine Optimization)** helps public pages be found using crawlable content, titles and descriptive metadata. **AA** is the middle WCAG conformance level and includes applicable A and AA criteria. **A/B** labels the two variants of a controlled test. **axe** and **Playwright** are tool names.

## Keep the stack small

| Defer until | Techniques |
| --- | --- |
| Public content changes frequently or a measured slow route needs it | **ISR (Incremental Static Regeneration)** refreshes static pages after deployment. Streaming SSR sends the ready parts of a page first. Edge rendering runs closer to users. Partial hydration and islands independently activate chosen UI regions. Start with the framework's normal public and protected route split. |
| The profiler shows repeated expensive work or long lists | Bundle analysis, manual preload, targeted memoization, virtualized lists, Web Workers and additional rendering optimization. Measure first and apply the smallest change. |
| Many screens share complex client state or data refresh rules | Context for stable shared UI state where useful. Redux Toolkit, Zustand, TanStack Query, signals, selectors, normalized client stores, broad optimistic updates and cross-tab sync are optional later choices. |
| Traffic or connectivity proves the need | GraphQL, server-sent events (SSE), WebSockets, HTTP ETags, batching, custom deduplication, infinite scroll, offline queues and manual HTTP/2 or HTTP/3 tuning. **ETag (entity tag)** lets a client check whether a response has changed. |
| Offline or push is approved as a product requirement | **PWA (Progressive Web App)** features, service workers, Cache API, IndexedDB, local or session storage, precaching, offline app shell, background sync, conflict resolution and push. Evaluate storage quotas, privacy and data lifetime first. |
| Independent applications or separate teams require stronger boundaries | Monorepo tooling, shared packages, micro frontends, module federation, plugin systems and elaborate architecture layers. Start by reusing feature modules and components in this codebase. |
| Product and security policy requires it | Specialist controls such as **SRI (Subresource Integrity)** for eligible third-party assets and iframe sandboxing for approved embeds. Review third-party scripts before use. Add **RTL (Right to Left)** layout and locale routing when target languages and translation ownership are confirmed. |
| There is deployed usage and an approved reason to collect more | Sentry or another error service, **RUM (Real User Monitoring)**, dashboards, session replay, source map upload, visual regression tooling and canary releases. Prefer redacted logs and targeted test evidence first. A human A/B trial needs an approved plan and accessibility check. |

A feature pull request records the selected technique, the actual file and why it fits, plus a way to verify it. Keep a row marked Planned until the implementation and test evidence exist. Update the [development record](<Development Status.md>) after each work session.
